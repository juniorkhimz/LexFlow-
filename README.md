# LexFlow

Legal practice management platform. React 19 + TypeScript + Vite + TanStack
Router + TanStack Query + Tailwind v4 + Radix UI + Supabase.

It is a client-rendered single-page app. The browser talks directly to
Supabase (Postgres, Auth, Storage); anything that needs a secret runs in a
Supabase Edge Function.

## Quick start

Requires Node 20+ and a Supabase project (create one at supabase.com).

```bash
npm install
cp .env.example .env        # Windows PowerShell: copy .env.example .env
```

From **Project Settings → API** in Supabase, put these in `.env`:

- `VITE_SUPABASE_URL` — the Project URL
- `VITE_SUPABASE_PUBLISHABLE_KEY` — the `anon` / publishable key (never the `service_role` key)

Link the CLI and apply the schema:

```bash
supabase login
supabase link --project-ref YOUR_PROJECT_REF   # 20 lowercase letters, from your project URL
npm run supabase:migrate                       # runs `supabase db push`
```

There are **14 migrations** in `supabase/migrations/` (`0001` to `0014`). They
must run in numeric order because later ones (billing triggers, the
quote-to-invoice RPC, invitations, plan limits) depend on earlier tables and
functions. If you prefer, paste them into the Supabase SQL Editor one at a time,
in order.

Then generate the database types (see the next section) and start the app:

```bash
npm run types:generate
npm run dev
```

Useful scripts:

| Command | What it does |
|---|---|
| `npm run dev` | Vite dev server |
| `npm run build` | Production build into `dist/` |
| `npm run preview` | Serve the production build locally (port 4173) |
| `npm run typecheck` | `tsc --noEmit` |
| `npm run test` | Vitest, single run (`test:watch` for watch mode) |
| `npm run supabase:migrate` | Apply migrations to the linked project |
| `npm run types:generate` | Regenerate `src/types/database.generated.ts` |

## Database types (generated)

Types come from the live database, not from hand-written definitions.

```
src/types/database.generated.ts   ← generated by the Supabase CLI. Never edit.
src/types/database.ts             ← hand-maintained. Re-exports the generated
                                    file and defines the aliases the app imports
                                    (Profile, Lead, LeadStatus, UserRole, ...).
```

Application code always imports from `@/types/database`, never from the
generated file directly.

**Regenerate after every schema change** (any new migration):

```bash
npm run types:generate
npm run typecheck
```

`types:generate` is defined in `package.json` as:

```json
"types:generate": "supabase gen types typescript --linked > src/types/database.generated.ts"
```

**Windows note:** run it through `npm run` (which uses `cmd.exe`) or via
`cmd /c "..."`. Redirecting with `>` directly in Windows PowerShell 5.1 writes
UTF-16, which TypeScript cannot read ("file is not a module"). If the command
fails (for example "Cannot find project ref"), the output file ends up empty.
Fix the cause (`supabase login`, `supabase link`) and run it again.

**Adding a new table or enum:** after regenerating, add the matching alias to
`src/types/database.ts`, for example
`export type Foo = Tbl["foos"]["Row"];`.

## What's implemented

**Foundation** — Vite + React 19 + TypeScript strict mode + path aliases,
Tailwind v4 via `@tailwindcss/vite` with a legal-SaaS ink/brass token set, a
validated Supabase client, and a full relational schema: foreign keys, indexes,
RLS on every table, a private document storage bucket with its own policies, and
server-side triggers that compute quote/invoice line totals and payment status.
Client-sent totals are never trusted.

**Auth** — sign up (atomically creates firm + admin profile via RPC), sign
in/out, forgot/reset password, session persistence, protected routes, and a
staff-vs-client role gate that routes each user to the right app surface.

**Every sidebar module is a real CRUD surface against Supabase, not a mock:**

- **Dashboard** — live KPIs, lead-pipeline and matters-by-practice-area charts, recent activity, upcoming deadlines, quick actions
- **Leads** — CRM with search/status filter, detail page, inline status updates, atomic convert-to-client, activity log, delete
- **Clients** — CRUD, KYC status, tabbed detail (matters, documents, quotes, invoices, payments, appointments, activity)
- **Matters** — table and card views, tabbed detail (overview, tasks, deadlines, documents, billing, notes, activity, AI assistant)
- **Tasks** — create, complete, filter, delete
- **Deadlines** — create, complete, critical deadlines visually flagged
- **Appointments** — book, associate client/lead/matter, status lifecycle, cancel
- **Quotes** — line-item builder, server-computed totals, send/accept/reject, duplicate, atomic convert-to-invoice (RPC)
- **Invoices** — line items, record payments, server-tracked balance and status via triggers
- **Documents** — real upload to private Supabase Storage, signed-URL download, rename, delete
- **Messages** — client-linked threads, real send/receive
- **Trust Accounts** — per-client trust ledger with database-enforced no-overdraw rule
- **Reports** — 7 aggregate queries and charts: revenue, outstanding invoices, quote/lead conversion, advocate workload, matter status, new clients
- **Settings** — profile, firm details, users and invitations, practice areas, billing, audit log
- **Client Portal** (`/portal`) — separate shell, RLS-restricted to the caller's own client record: matters, documents, quotes, invoices, appointments, messages
- **Platform admin** (`/admin`) — cross-firm overview for the SaaS operator only

Reusable UI kit: PageHeader, StatusBadge, DataTable, EmptyState / LoadingState /
ErrorState, ConfirmDialog, SearchInput, form fields, PasswordInput,
LineItemEditor, CurrencyDisplay / DateDisplay, ActivityTimeline.

## Deliberately left out

Not mocked, just not built:

- **Settings → Notifications and Security tabs.** No real backing data source
  was in scope, so rather than show controls wired to nothing they are not
  rendered. Users, Firm, Practice Areas, Billing and Audit Log are real.
- **M-Pesa API integration.** Payments support `mpesa` as a recorded method, but
  there is no live Daraja API call. The schema (`payments.reference`) is ready.
  Paystack subscriptions (below) are separate from this.
- **Global search** debounces client-side and queries 5 tables directly. That is
  fine at current scale; it would move to a Postgres full-text index or an Edge
  Function if result volume grows.

## Known deviations from the original brief

- **TanStack Start is not wired in.** Only `@tanstack/react-router` is used, as a
  client-rendered SPA. Start needs its own SSR entry files.
- **Routes are code-based** (`src/router.tsx`), not file-based with codegen. Both
  are first-class in TanStack Router; migrate to file conventions if you prefer.
- **Bundle size.** The production build is a single ~1.4 MB (≈400 KB gzipped)
  JS chunk. Route-level code splitting (`React.lazy` / dynamic `import()`) is the
  obvious next optimisation.

## Edge Functions and secrets

Seven functions live in `supabase/functions/` (plus `_shared/`):

| Function | Purpose | Secrets it needs | Deploy flag |
|---|---|---|---|
| `admin-firms-overview` | Cross-firm data for platform admins | none beyond injected | |
| `ai-gateway` | Matter-context AI (synthetic or disabled) | `GEMINI_API_KEY`, `AI_MATTER_CONTEXT_MODE` | |
| `gemini-chat` | Floating general-purpose assistant | `GEMINI_API_KEY` | |
| `send-invitation-email` | Emails invitation links | `RESEND_API_KEY`, `APP_URL`, optional `INVITE_FROM_EMAIL` | |
| `paystack-initialize-transaction` | Starts a subscription checkout | `PAYSTACK_SECRET_KEY` | |
| `paystack-cancel-subscription` | Cancels a subscription | `PAYSTACK_SECRET_KEY` | |
| `paystack-webhook` | Receives Paystack events, writes `subscriptions` | `PAYSTACK_SECRET_KEY` | `--no-verify-jwt` |

`SUPABASE_URL`, `SUPABASE_ANON_KEY` and `SUPABASE_SERVICE_ROLE_KEY` are injected
by Supabase automatically; do not set them yourself.

Set secrets (server-side only; never in `.env`, never `VITE_`-prefixed):

```bash
supabase secrets set PAYSTACK_SECRET_KEY=sk_test_...
supabase secrets set GEMINI_API_KEY=...
supabase secrets set RESEND_API_KEY=re_...
supabase secrets set APP_URL=https://your-deployed-site.com
supabase secrets set AI_MATTER_CONTEXT_MODE=synthetic     # or leave unset to disable
# optional
supabase secrets set GEMINI_MODEL=gemini-2.5-flash
supabase secrets set INVITE_FROM_EMAIL="LexFlow <invites@yourdomain.com>"
```

Deploy:

```bash
supabase functions deploy admin-firms-overview
supabase functions deploy ai-gateway
supabase functions deploy gemini-chat
supabase functions deploy send-invitation-email
supabase functions deploy paystack-initialize-transaction
supabase functions deploy paystack-cancel-subscription
supabase functions deploy paystack-webhook --no-verify-jwt
```

Check what is set and deployed:

```bash
supabase secrets list       # shows names and digests only, never values
supabase functions list
```

Functions pick up new secrets without a redeploy. You may skip any service you
are not using yet; the core CRUD app works without them.

To run functions locally, use `supabase functions serve` (needs Docker Desktop)
with the same secrets in `supabase/.env.local` (gitignored).

## Subscriptions (Paystack)

The `subscriptions` table (`0008_subscriptions.sql`, extended by
`0014_paystack_billing.sql`) tracks each firm's paid plan for LexFlow itself,
separate from the invoices a firm sends its own clients. Paystack is the single
source of truth. The table is never client-writable: RLS grants read-only access
to admins and partners, and only the `paystack-webhook` function writes it.

**Why Paystack and not Stripe:** Stripe does not support Kenya as an account
country. Using it would require incorporating a business in a supported country,
getting a US EIN and opening a US bank account. Paystack operates directly in
Kenya, with native M-Pesa support.

**Capability difference from Stripe:** Paystack has no hosted self-service
billing portal. Instead, Settings → Billing has a **Cancel subscription** button
that calls Paystack's API server-side. There is no in-app "update payment
method" or "view past invoices" flow; a firm resubscribes if its card fails.
Know this before relying on it for real customers.

**Setup:**

1. Create a [Paystack](https://paystack.com) account.
2. In Dashboard → Products → Plans, create a plan for each tier (monthly interval).
3. Copy each plan code (`PLN_...`) into `src/lib/billing-plans.ts`.
4. Map the same plan codes to plan names in `planFromPlanCode()` inside `supabase/functions/paystack-webhook/index.ts`.
5. Set `PAYSTACK_SECRET_KEY` and deploy the three Paystack functions (see above).
6. In Paystack → Settings → API Keys & Webhooks, set the webhook URL to
   `https://<project-ref>.supabase.co/functions/v1/paystack-webhook`.
   This is project-specific; a webhook registered for a dev project will not fire for production.
7. Make sure migration `0014_paystack_billing.sql` has been applied.
8. Test with Paystack's [test cards](https://paystack.com/docs/payments/test-payments) before switching to `sk_live_` keys.

Only `admin` and `partner` roles can manage billing, enforced both client-side
and inside the Edge Functions.

> **Verify before going live.** The webhook resolves which firm an event belongs
> to using `metadata.firm_id` on `charge.success`, which is documented Paystack
> behaviour. Whether `metadata` also propagates onto the separate
> `subscription.create` event has not been verified against live Paystack
> traffic. The webhook falls back to matching the customer email against
> `profiles.email`. Run one complete test-mode subscription and confirm a
> `subscriptions` row is created for the correct firm before relying on this.

## AI features (Gemini)

Both AI functions use the same `GEMINI_API_KEY`, which never reaches the browser.

### Assistant widget (`gemini-chat`)

A floating chat widget (bottom-right, staff app only). It is a general-purpose
assistant with **no access to firm data**, and that is deliberate. See the
comment at the top of `supabase/functions/gemini-chat/index.ts`.

Optionally pin a model with `GEMINI_MODEL` instead of Google's auto-updating
alias. Google's model lineup changes often and older models are shut down on
several months' notice, so check the
[current model list](https://ai.google.dev/gemini-api/docs/models).

### Matter-context AI (`ai-gateway`)

A separate function for AI features that need to see a matter's content (a
"matter copilot": summaries, "ask this matter about X"). It is the single,
auditable place where the question of data access gets decided.

The current state is deliberate, not a placeholder:

- Every request is authorization-checked first, in every mode, via a real RLS-scoped query.
- Every request is logged to `activities`.
- `AI_MATTER_CONTEXT_MODE` is either `disabled` (default if unset: no Gemini call at all) or `synthetic` (runs the real prompt pipeline against a fixed, clearly-fake sample matter, so the feature is demoable with zero privacy exposure).
- **There is no "live" mode.** `getLiveMatterContext()` is a stub that throws. Code that does not exist cannot leak privileged data.

Before implementing live mode, you would need: a redaction/minimisation
strategy, client disclosure (privileged material leaving your infrastructure for
a third-party model), exact logging of what was sent, and legal sign-off.

Try it safely: on a matter's detail page, open the **AI Assistant** tab. With
`AI_MATTER_CONTEXT_MODE=synthetic` you get a real Gemini response about a sample
matter, under a warning banner confirming it is demo data.

## Invitations (adding teammates)

Added by `0009_invitations.sql` so a second person can join an existing firm
rather than creating a new one.

1. **Settings → Users** (admin/partner only): enter a colleague's email and role, click Invite.
2. If email sending is configured, they receive a link. If not, the link is shown in the UI to copy and share yourself. Invite creation always succeeds; email delivery is a separate, non-blocking step.
3. They open `/invite/<token>`, see which firm and role they are joining, set a password, and land in your firm with the assigned role.

Invitations are validated against the invited email address, expire after 7
days, and can be revoked before use.

**Real email delivery (Resend):** create an account at resend.com, create an API
key, then `supabase secrets set RESEND_API_KEY=re_...` and deploy
`send-invitation-email`. Without a verified sending domain, Resend's shared test
sender can only deliver to the email on your own Resend account. To email real
people, verify a domain and set `INVITE_FROM_EMAIL`. Also set `APP_URL` so links
point at your deployed site.

## Auth emails (Supabase SMTP)

Password reset, email confirmation and magic-link emails are sent by Supabase
Auth's own built-in system, separate from the invitation emails above. The
default sender is heavily rate-limited (a handful of emails per hour) and meant
for testing.

Point Supabase Auth at Resend:

1. In Resend, open SMTP and copy the credentials (host, port, username; your API key is the password).
2. In Supabase → Project Settings → Authentication → SMTP Settings, enable Custom SMTP and enter them, with a sender address on your verified Resend domain.

The same verified-domain caveat applies.

## CSV import (onboarding)

Leads, Clients and Matters each have an **Import CSV** button that:

1. Parses with PapaParse (quoted fields and embedded commas handled correctly).
2. Auto-guesses a column mapping from the headers, with a manual override per column.
3. Validates every row (required fields, email format, numbers, dates) before import. Invalid rows are skipped and reported with a reason; valid rows still import.
4. Bulk-inserts in chunks of 200 for Leads and Clients. **Matters import one row at a time**, because of the unique `(firm_id, matter_number)` constraint: one duplicate in a batch would abort the whole batch with no per-row detail.
5. Logs one `activities` entry per import, not per row.

**Import Clients before Matters.** A matter references its client by name,
resolved by case-insensitive exact match against existing clients.

Not done: document bulk-upload, and "undo import". A mis-mapped import needs
manual cleanup.

## Plan-based feature gating

`0010_plan_limits_and_gating.sql` and `0011_storage_quota_gating.sql` enforce
limits in the database, not just the UI:

- `plan_limits` defines seats, client-portal access and storage per tier (`free`: 1 staff seat, no portal; `starter`: 5 seats; `pro`: 25 seats plus portal; `enterprise`: unlimited plus portal). Edit this table in SQL to change tiers; it is platform config.
- The `invitations` INSERT policy checks the firm's plan before allowing a staff or client-portal invite. `accept_invitation()` re-checks as a safety net.
- Storage quotas (document count and total size) use the same pattern.
- The frontend (`usePlanLimits`, used in Settings → Users) shows "3 of 5 seats used" and disables inviting past the limit. It is a friendlier front door to the same rule; the database refuses it either way.

**Keep three places in sync when plan definitions change:** the `plan_limits`
table, the CHECK constraint on `subscriptions.plan` (`0008_subscriptions.sql`),
and `src/lib/billing-plans.ts`.

## Trust accounting

Tracks money a firm holds on a client's behalf (retainers, settlement funds),
separately from operating funds and per client. One hard rule: a firm can never
disburse or transfer more of a specific client's trust money than that client has
on deposit, even if the firm's total trust balance is higher. The actual
enforcement is the `enforce_trust_balance_nonnegative()` trigger in
`0012_trust_accounting.sql`, not a UI check.

**Sidebar → Trust Accounts** shows every client with a nonzero balance, a
running per-client ledger (deposits, disbursements, transfers to operating), and
a "Record transaction" flow that surfaces the database's rejection message
verbatim if an entry would overdraw.

Not modelled: reconciliation against bank statements, and bar-association
specific audit report formats. Those need domain input from someone who has
filed one.

## Platform admin panel

A firm's `admin` role is scoped to its own firm by RLS. A **platform admin** is
someone who works for you, the SaaS operator, and needs to see across firms.
`0013_platform_admins.sql` plus `/admin` provide that without any blanket "bypass
RLS" policy:

- `platform_admins` is its own table, unrelated to any `firm_id`. Its policy only lets someone check their own membership.
- Cross-firm reads go through exactly one Edge Function, `admin-firms-overview`, which re-verifies platform-admin status server-side and then uses the service-role key.
- `/admin` is its own top-level route with no staff sidebar, so it could be split into a separate deployment later.

Add yourself (SQL only, by design):

```sql
select id, email from auth.users where email = 'you@example.com';
insert into platform_admins (id, full_name) values ('<your auth.users.id>', 'Your Name');
```

Not modelled: live revenue totals (the panel reads `subscriptions.plan` and
`status` from this app's database; use the Paystack dashboard for revenue),
impersonating a firm's login, or editing any firm's data from the panel.

## Automated tests

Vitest + Testing Library, focused on the highest-risk logic rather than blanket
coverage:

- `src/lib/billing-math.test.ts` — the quote/invoice line-total formula (extracted to `src/lib/billing-math.ts` so it is testable). It must stay in sync with `set_line_total()` in `0005_billing_triggers.sql`; the SQL trigger is the source of truth and this test catches drift in the client-side preview.
- `src/lib/utils.test.ts` — currency/date formatting and class merging. The KES assertion uses a case-insensitive match because `Intl` formats the code as `Ksh`.
- `src/components/ui/status-badge.test.tsx` — including graceful handling of a status not in `TONE_MAP`.
- `src/components/ui/password-input.test.tsx` — show/hide toggle.
- `src/components/ui/pagination.test.tsx` — next/prev logic, with and without an exact Supabase count.

Run with `npm run test` or `npm run test:watch`. There are no integration or
end-to-end tests yet.

## Deployment

The app builds to static files and can be hosted on Vercel, Netlify, Cloudflare
Pages or any static host. There is no separate backend server beyond the Edge
Functions.

**Current verified status:** `npm run typecheck` and `npm run build` pass.
Run `npm run test` and click through the app in `npm run preview` before every
deploy.

### Checklist (each item breaks something silently if skipped)

1. **Build and preview locally.**
   ```bash
   npm run typecheck
   npm run test
   npm run build
   npm run preview      # http://localhost:4173
   ```
   Sign up, create a lead, a client and a matter, and refresh on a deep link such as `/leads`. A successful build does not prove the app works.

2. **Database.** Apply all 14 migrations to the production Supabase project (`supabase link` to it, then `npm run supabase:migrate`). A fresh project has none of the schema. Verify with `supabase migration list`.

3. **Regenerate types** if the schema changed: `npm run types:generate`.

4. **Edge Functions.** Deploy all seven and set their secrets (see [Edge Functions and secrets](#edge-functions-and-secrets)). Include `APP_URL`.

5. **Frontend host.** Import the repo. The framework is Vite, the build command is `npm run build`, the output directory is `dist`. SPA routing rewrites are already configured in `vercel.json`, `netlify.toml` and `public/_redirects`, so deep links and refreshes work.

6. **Frontend environment variables.** Set exactly two in the hosting dashboard (`.env` is gitignored and never deployed):
   - `VITE_SUPABASE_URL`
   - `VITE_SUPABASE_PUBLISHABLE_KEY`

   Both are safe in the browser. No other secret belongs on the frontend host.

7. **Supabase Auth URLs.** In Authentication → URL Configuration, set **Site URL** to the deployed address and add `https://your-domain/**` to **Redirect URLs**. Without this, password-reset and invitation links point to the wrong place.

8. **Auth email.** Configure custom SMTP (see [Auth emails](#auth-emails-supabase-smtp)).

9. **Paystack webhook** URL pointed at the production function (if using billing).

10. **First test.** Sign up on the live site, create a lead, invite a teammate, and run one test-mode Paystack subscription, confirming the `subscriptions` row.

11. **`robots.txt`** currently disallows all crawling, which is correct for an authenticated app with no public pages. Revisit if you add a public marketing page.

### Not set up

- **CI/CD.** No GitHub Actions or similar. Deploys happen when you push to the branch your host watches. A minimal pipeline running `typecheck`, `test` and `build` on every push would be worthwhile.
- **Staging environment.** One production Supabase project and one frontend deploy are assumed. A separate staging project to test migrations against is advisable.
- **Error tracking.** No Sentry or similar. Production errors only surface if a user reports them. Add this before real customers use the app.

## Security notes

- **RLS is the enforcement boundary** (`supabase/migrations/0002_rls_policies.sql`), not frontend checks. Every table is scoped by `firm_id`; client users see only rows linked to their own `clients.id` via `auth_client_ids()`. `requireStaff` in `src/router.tsx` is a UX redirect on top of that.
- **The `documents` storage bucket is private.** Always fetch through `supabase.storage.from('documents').createSignedUrl(...)`, never a public URL.
- **Totals are computed in Postgres** (`0005_billing_triggers.sql`), never trusted from client input.
- **The service-role key** must never appear in this codebase or in any `VITE_` variable. It is used only inside Edge Functions, as an injected Supabase secret.
- **Paystack, Gemini and Resend keys** are Edge Function secrets only: never in `.env`, never `VITE_`-prefixed, never in the browser bundle.
- **`subscriptions` writes** are restricted to the service-role webhook by RLS. No client role, not even `admin`, can write it.
- If a real key is ever committed or pasted somewhere public, treat it as compromised: rotate it at the provider and re-run `supabase secrets set`.

## Launch checklist and commercial readiness

### What an authenticated SaaS app needs, and what was done

Closed:

- Custom 404 page (`src/routes/not-found.tsx`)
- Per-page `<title>` (`useDocumentTitle`)
- Meta description and Open Graph tags (`index.html`)
- Favicon (`public/favicon.svg`)
- `robots.txt`, deliberately `Disallow: /`
- Privacy Policy and Terms of Service pages (`/privacy`, `/terms`), linked from signup. These are **structural placeholders only**, banner-labelled as not legally reviewed.
- A cookie / local-storage consent banner disclosing what is stored (session and theme). Update it the day analytics or any tracking is added.

Not applicable while there is no public marketing page: CTA above the fold,
`sitemap.xml`, sticky mobile CTA. Alt text and image compression become relevant
once a logo or OG image exists.

### Capabilities closed

- Multiple people per firm (invitations)
- The "signed up but no profile" dead end (`/complete-setup`)
- Billing-manipulation integrity gap (negative quantity/discount constraints)
- Subscriptions wired to Paystack checkout and webhooks
- AI assistant scoped deliberately (no firm-data access)
- Transactional invitation email (Resend) with graceful manual-link fallback
- Plan-based gating for seats, portal access and storage, enforced in the database
- Audit log UI (Settings → Audit Log) over the `activities` table

### Still code-shaped

- Route-level code splitting (bundle is ~1.4 MB)
- CI pipeline, staging environment, error tracking (see Deployment)
- Integration and end-to-end tests
- In-app payment-method update and past-invoice views (not possible via Paystack without extra work)

### Not code: needs you, a lawyer, or a business decision

- **Terms of Service, Privacy Policy and data-protection compliance.** This app holds client-privileged legal data. Get a real assessment of what applies in your market (for Kenya, the Data Protection Act 2019). A law-firm customer will ask before trusting you with client data.
- **A support channel** (even a monitored email) and an incident/outage communication plan.
- **Backup and disaster recovery.** Supabase makes automated backups on paid tiers, but you need a *tested* restore process.
- **Payment processor compliance.** Paystack is used in test mode until you complete live verification with them.
- **Real usage.** The largest remaining risk is not a missing feature; it is the first real firm hitting a workflow nobody tested.

**Honest read:** this is a capable MVP with real multi-tenant isolation, an
invitation flow, real billing and a scoped AI feature, good enough to onboard a
friendly first customer who understands it is early. It is not yet ready to be
marketed broadly with real client data at scale. That gap is mostly the non-code
list above.
